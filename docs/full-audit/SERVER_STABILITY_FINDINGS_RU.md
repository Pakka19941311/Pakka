# Серверная устойчивость: f251 → 6279 → индекс опор

Работа относится к исправлению зависания выданного f251 ZIP. Новые сундуки, предметы, карта и другие функции из рабочего Pakka сюда не переносились. Числа и SHA исходников: `SERVER_STABILITY_METRICS.json`. Сохранения, токены и содержимое пользовательского инвентаря в отчёт не включены; SQLite читалась только из отдельных локальных копий.

## Измерения на одинаковом сохранении

Последовательные прогоны без параллельной нагрузки команды. 600 полноразмерных шагов 60 Hz (10 секунд игрового времени), 1 151 монстр, обычная симуляция, один подключённый герой из копии. RNG фиксирован для сравнения состояния. Наблюдающие обёртки одинаковы во всех вариантах. Это CPU replay, а не измерение FPS Godot.

| Вариант | Суммарный CPU replay | p50 шага | p95 | p99 | Максимум |
|---|---:|---:|---:|---:|---:|
| f251 | 8 450,447 мс | 13,796 мс | 20,465 мс | 25,068 мс | 41,269 мс |
| 6279, освобождение старой цели | 6 407,402 мс | 11,087 мс | 15,914 мс | 18,341 мс | 23,205 мс |
| 6279 + индекс опор | 1 579,612 мс | 2,506 мс | 3,980 мс | 4,913 мс | 10,034 мс |

Состояние после последних двух прогонов полностью совпало через `isDeepStrictEqual`: позиции, здоровье, смерти, таймеры, предметы и квесты не изменились вследствие индекса. Опоры не удалялись; высоты, вода, преграды и безопасные зоны сохранены. Тесты дополнительно сравнивают исходный exhaustive support на всех краях реальных опор, на 9 000 точках карты и при обычном `collision.resolve` на краях/ступенях/склонах.

## Реальная HTTP последовательность

`stability-http-fire-ice.mjs` запускает настоящий сервер и SSE, использует существующие одноразовые native hero fixtures и отправляет обычные HTTP destination / single attack. Никакие монстры не переставляются, не отключаются и не получают искусственный HP; время не переводится вручную. После переноса огонь → лёд выполнено ещё 8 секунд наблюдения.

После индекса: 279 snapshot-пакетов; максимальный промежуток 147,522 мс; пять input ACK за 3,522–20,013 мс. Огненный counter нанёс один удар на 68 HP. Обычный шаг в сторону от ледяной линии сохранил HP. Старые огненные цели освобождены. Не было `advance` дольше 50 мс. Пятисекундный timeout клиента не увеличивался.

Исторические ошибки сохранены отдельно и не объявлены успешными: `stability-line-source-01` (реальный server stall), `stability-line-source-02` и `stability-line-packaged-01` (cold-load timeout до fixture), HTTP `stability-http-fire-ice-01..03` (рост catch-up до исправления индекса). Городской `deadline-packaged-city-01` ещё требует повторной диагностики границы render/capture: отсутствие guardhouse PNG само по себе не доказывает конкретную причину ожидания.

## Воспроизводимые инструменты

- `stability-private-replay.mjs <копия server> <exact world-final> <hero id> <новый отчёт.json>` читает private SQLite, работает с памятью и пишет полный отчёт только рядом с копией. Его полный результат нельзя коммитить или публиковать.
- `stability-http-fire-ice.mjs <новый QA каталог>` создаёт только синтетическое сохранение; отчёт клиента является отдельным шагом.
- `stability-probe.mjs` включается исключительно диагностическим запускателем и не изменяет clock, ответы HTTP или политику мира.
- `godot_run_checked.py --qa-user-root <QA каталог>` изолирует только дочерние APPDATA/LOCALAPPDATA. Это позволяет проверять записываемый shader cache без доступа к личным save. По Godot 4.6 Windows data path берётся из APPDATA, cache path — из LOCALAPPDATA ([официальный исходник](https://github.com/godotengine/godot/blob/4.6/platform/windows/os_windows.cpp)). Исходные engine/project settings не меняются; отдельный root certificate warning этим не устраняется.
