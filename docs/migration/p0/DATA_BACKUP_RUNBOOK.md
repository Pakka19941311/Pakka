# P0-02 — резервирование и восстановление

Git доступен и содержит исходники, игровые ассеты, определения персонажей/предметов и код сохранения. «Нет доступа к базе» ниже относится только к личному файлу SQLite на компьютере игрока и его браузерному профилю. Наличие кода в Git не подтверждает резервирование личного прогресса. Фактическое расположение БД надо установить по запуску: указанный далее Windows-путь — значение по умолчанию переносимой сборки, не подтверждённый путь на ПК владельца.

Статус реальных данных: **blocked**. Действующая база `%LOCALAPPDATA%\Varendor\world-beta-v1\world.sqlite`, профиль браузера и pending-операции Никиты не доступны. Ни ZIP ТЗ, ни Git, ни синтетическая база тестов их не заменяют.

Подготовлен `scripts/p0-backup-world.mjs`. Он открывает исходную SQLite read-only, фиксирует читаемое состояние транзакцией, использует SQLite online backup с WAL, открывает копию отдельно, проверяет integrity и полное совпадение всех пяти таблиц/JSON состояния, считает персонажей и уникальные UID. Неизвестная схема, пустая база без персонажей и дублированный UID дают отказ без автоматического ремонта. Каждый запуск создаёт новый каталог, существующая копия не перезаписывается. Хранилище внутри Git запрещено.

Пять тестов `tests/p0-backup.test.mjs` пройдены на синтетических данных, включая запуск изолированной копии и повтор старого commandId без второго расхода. Это проверка инструмента. Реальное восстановление владельца и браузерного pending не выполнено.

## Порядок для оператора

1. Установить фактический процесс, путь данных, origin и профиль браузера, выбранного героя. Прочитать server.lock как указатель процесса, не удалять его для обхода блокировки. Сверить с запущенным процессом.
2. Для точной общей контрольной точки завершить текущую предметную операцию с прежним id. Если ответ неизвестен, сохранить pending и оставить исход unknown до получения receipt. Не делать новый бросок.
3. Сохранить восемь ключей из UI_PROFILE_SCHEMA в закрытый локальный файл; не выводить bearer в чат или Git. Не очищать браузер и не менять его профиль. Секретная копия требует отдельного защищённого места.
4. Предпочтительно штатно остановить игру командой `stop` в окне сервера. Утилита поддерживает активный WAL, но не делает браузер и продолжающий работать мир одной атомарной копией сама по себе.
5. Выполнить из checkout команду ниже. В переносимом Windows-пакете есть `runtime/node.exe`; отдельно Node устанавливать не обязательно. Проверено в этой среде на Node 24.19.0/Linux; запуск утилиты на Windows пока не проверен.

```powershell
& 'C:\папка-игры\runtime\node.exe' '.\scripts\p0-backup-world.mjs' "$env:LOCALAPPDATA\Varendor\world-beta-v1\world.sqlite" "$env:LOCALAPPDATA\Varendor\p0-private-backups"
```

6. `verification.json` подтверждает только выполненную проверку конкретного файла. Проверить identity выбранного героя и все поля его имущества; сравнить browser/UI данные отдельно. В Git идёт лишь обезличенное свидетельство проверки, не SQLite, токены, профиль или полные строки таблиц.
7. Сохранённую проверенную копию больше не использовать для запуска. Сделать **вторую рабочую копию** в отдельном каталоге восстановления. Контрольный Windows launcher поддерживает `--data-dir` и `--port`; использовать другой порт и изолированный профиль браузера, чтобы не перепутать оригинал и восстановленный мир.

```powershell
& 'C:\папка-игры\runtime\node.exe' 'C:\папка-игры\server\launch-world.mjs' --data-dir 'C:\закрытый-каталог\restore-working-copy' --port 4174 --no-browser
```

8. Прежде чем менять данные в тесте, сравнить полное состояние. Запуск симуляции закономерно меняет время, activeUntil, движение и windup; это фиксируется отдельно от неизменных characterId/itemUid/количеств/+N/валюты/прогресса. После входа прежним героем восстановить pending тем же id, повторно открыть БД и проверить квитанцию/единственный расход.
9. Только после этого закрывать P0-02/DATA-01/DATA-02/G0. До нового прогресса возможен возврат совместимого кода и копии. После нового прогресса подстановка старой базы требует отдельного контролируемого решения и не считается безопасным откатом.

Дефект baseline при закрытии сервера с активным SSE исправлен отдельно в `07408b7`; см. SHUTDOWN_FIX. Действующая старая Windows-сборка этого исправления не содержит. Утилита backup не использует этот shutdown path. Личное резервирование и восстановление остаются невыполненными.
