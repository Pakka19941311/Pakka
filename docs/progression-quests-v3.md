## Условия и обязательная привязка к миру

`ProgressionWorldBindings` содержит `revision`, `markers` и `huntKeys`. Пустая привязка используется по умолчанию. Новое задание с отсутствующей привязкой нельзя принять: `quest-world-not-ready`. Selector отдельно сообщает `requirementsAvailable:false`. Готовое старое книжное испытание не теряет право сдачи из-за отсутствия новых слотов.

Исследовательские записи задают **семантические ключи**, а не выдуманные существующие объекты:

| Задание | Требуемые доказательства |
|---|---|
| 110 | `q110:outlook-a/b`: две разные обзорные точки L03 |
| 120 | `q120:shore-a/b`: два дальних берега L06 |
| 125 | `q125:mine-exterior`: обследование наружного комплекса L05 |
| 130 | `q130:chamber-a/b/c`: три разные рабочие камеры L05, пространство mine |

Адаптер `src/server/progression-quest-world.ts` связывает ключи с существующими дорогами/камерами, сохраняя координаты в исходном авторинге. Для поверхности используется серверное `z=-GodotZ`. Все 14 маркеров текущего FinalWorld проходят проверку существования источника, пространства, административной локации и коллизии для героя радиуса 0.46. При пропавшем/заблокированном источнике соответствующее поручение нельзя принять; точка не переносится автоматически на произвольное место.

|---|---|
| 110 a/b | `world_layout.json`, road living-forest-loop, points_xyz[3]/[18] |
| 120 a/b | road fort-lake, [18]/[33] |
| 125 | road mine-cave-link, [3] |

Сервер наблюдает активные поручения каждые 250 мс. Осмотр требует входа извне в радиус 4 м, видимости и пребывания минимум 1 с. Непрерывность проверяется по серверному времени, скорости и generation; смерть, переход/переподключение и скачок положения сбрасывают незавершённый маршрут наблюдателя. Появление прямо на конечной точке не даёт зачёта. Для 141 нужны все три камеры по порядку; нахождение только в cistern не завершает маршрут. Клиент получает следующий ориентир в objective.target и показывает направление/расстояние. Полные проходимость и боевой риск на нужных уровнях ещё требуют нативной маршрутной приёмки; проверка точки collision не выдаётся за неё.

QUEST-115 считает восемь MOB-06 / `v3_forest_spider` уровня 10–14 в L03-A. Эта техническая привязка выбрана по имеющейся ведомости: там предусмотрены 40 экземпляров нужного вида. Статическая ведомость не подтверждает их готовность в runtime; разрешающий `huntKey` добавляется только после проверки фактических слотов и характеристик.

## Состояние, выдача и действующие hooks

`character.progressionQuests = {version:1,quests,legacy,...}`. У записи задания есть `status`, `classId`, `acceptedAt`, `kills`, `killKeys`, `evidence`, `xpGranted`, `pendingItems`, необязательный `rewardChoice`, а также происхождение миграционного зачёта. Статусы: active, ready, reward-pending, claimed.

Зарегистрирован WorldCommand `{type:'progressionQuest',questId,action:'accept'|'claim',rewardChoice?}`. Только QUEST-125 требует `rewardChoice:weapon_scroll|armor_scroll`; при первой сдаче выбор фиксируется. Повторное получение pending не позволяет заменить свиток.

Интеграция выполняет связанные действия:

1. На загрузке/импорте после общей нормализации уровня вызывается `initializeProgressionQuests`. `progression-quest-import.ts` валидирует и сохраняет bookQuests/ledger/pending; UID ожидающих наград включены в общую import-проверку и переназначаются один раз, как UID сумки/склада. Оригинал private import сохраняется штатной транзакцией.
2. Accept/claim выполняются через существующий WorldStore command receipt. Контекст NPC берётся из реестра сервера: живой герой, конкретный выдающий NPC, то же пространство, дистанция до 3.2 м с учётом высоты, LOS. Клиент не передаёт цену, XP, класс, completed или reward items. Для QUEST-141 валидированное возвращение порождает service event до окончательной проверки сдачи.
3. Существующая обработка смерти передаёт один credited kill event с metadata реального spawn slot. World adapter передаёт marker/service события. Публичной клиентской команды completed/progress нет.
4. Проект героя и receipt сохраняются атомарно. При первом claim XP выдаётся один раз, предметы добавляются или остаются в постоянном pending. При получении уровня применяется штатный пересчёт/лечение уровня; retry его не повторяет.
5. Старый `bookQuest` стал совместимым alias общей ledger. Он может выдать ту же сохранённую награду у прежнего Ардена или Северина после проверки расстояния/высоты/LOS. Новый native UI направляет новые испытания к Северину; у Ардена видны сохранённые ready/pending награды. Старые `big/rift_boss → ready` ветви удалены. BOOK_ITEMS origin и затронутый прежний тест обновлены; способности и цены не меняются.

`snapshot.progressionQuests` отдаёт id/title/level/giverId/status/xp/rewards/rewardChoices/rewardChoice?/objectives/pendingItemCount/requirementsAvailable/prerequisite/legacyCredit. У охоты есть count/required и название вида/участка; у незавершённого маркера — optional target:{x,z,spaceId}. `reward-pending` преобразуется в UI-статус pending. При requirementsAvailable:false новое принятие недоступно и в UI, и на сервере. У Роэна кнопка из стартового диалога открывает восемь поздних карточек, у Северина открываются две книжные карточки и кнопка обычной покупки 10–40. Старые стартовые поручения не заменены.

Исход claim содержит `{questId,status,xpAwarded,delivered,pendingItemUids}`. Запись delivered имеет `{id,count,inventoryUid}`: count — выданное этим вызовом количество, а не ссылка на полную актуальную стопку. Совместимые расходники объединяются с существующими стопками даже при полной сумке. Материалы соблюдают предел 999; остаток получает постоянный pending с сохранённым UID. Книги не объединяются в стопку. Повтор или получение после перезапуска не начисляет XP ещё раз. Идентификаторы книг берутся только из фактического `SKILL_BOOKS` по классу героя.

## Явная миграция прежних прав

| Источник | Результат |
|---|---|
| `quest:0` | Неактивное старое числовое поручение сохраняется как есть |
| `quest:1` | Старое поручение охоты активно; не считается новым QUEST-110 |
| `quest:2` | Старое условие убийств пройдено; прежняя следующая стадия сохраняется |
| `quest:3` | Прежний mini пройден; прежняя стадия big сохраняется |
| `quest:4` | Старый числовой цикл завершён; новые награды автоматически не выдаются |
| `book_{class}_50` active / ready / claimed | Соответствующий QUEST-150 active / ready / claimed |
| `book_{class}_60` active / ready / claimed | Соответствующий QUEST-160 active / ready / claimed |

Старые числовые значения и полная копия bookQuests сохраняются в `legacy`; отдельные Q-R/Q-I/Q-M записи остаются под собственными IDs и не угадываются из числа 0–4. Готовое старое испытание не требует повторно убивать новые цели. Старое active60/ready60 сохраняет исключение из нового prerequisite, если раньше книгу 50 не сдавали: уже открытое право не теряется. Новое принятие 60 такого исключения не имеет.

`claimed` означает израсходованное бесплатное право: новой книги и ретроактивного XP нет, даже если предмет затем продали или он отсутствует. Одно владение купленной/изученной книгой при отсутствии consumed entitlement награду не отменяет — это прямое требование принятого текста.

Особый случай: существующая старая книга при `bookQuests=claimed` находится в lootBuffer. Она **перемещается**, с тем же UID и количеством, в постоянный pending соответствующего квеста; новая книга не создаётся, XP не добавляется. Исходная буферная запись сохраняется в миграционном аудите. Получение при освободившемся месте возвращает существующую вещь. Неоднозначные повторяющиеся UID отклоняются без изменения исходного состояния.

Новый pending сразу отражается в совместимом bookQuests как claimed, потому что право уже превращено в конкретную вещь. Если старый путь успел записать claimed поверх нового active/ready, факт получения имеет приоритет; конфликтующая запись архивируется и повторного приза нет. Это дополнительная защита, а не разрешение оставить два обработчика выдачи при интеграции.
