# Ошибка служебного запуска Godot 12 сентября

Пользователь сообщил об окне ошибки `Godot_v4.6.3-stable_win64.exe`: чтение памяти по адресу `0x58`. Примерно в 12:38–12:39 UTC служебный вызов `--headless --check-only --script res://scripts/progression_quests.gd` без отдельного журнала завершился `CrashHandlerException`, signal 11, до нормального запуска проекта. Отладочных символов в бинарнике нет; конкретный стек вызовов не восстановлен.

Тот же бинарник, проект и скрипт, запущенные через `godot_run_checked.py` с заранее созданным абсолютным `--log-file`, завершились в 12:40:15 UTC с exit 0, пустым stderr и без ошибок скрипта. Связь со стандартным недоступным `user://` и логгером подтверждается поведением и кодом движка: [Godot 4.6.3 logger.cpp](https://github.com/godotengine/godot/blob/4.6.3-stable/core/io/logger.cpp#L155) вызывает метод результата открытия файла без проверки на null. Это обоснованный вывод о пути сбоя; символизированного crash dump нет.

Исправление рабочего процесса: все проверки используют защищённый запускатель; добавлен отдельный `--check-script`, проверка пути скрипта и фиксация Windows exception exit codes даже при пустом журнале. Если журнал создать нельзя, Godot не запускается. Игровой `launch-native.mjs` уже создаёт уникальный доступный журнал перед запуском экспортированного EXE. Настройки Windows и личные сохранения не менялись.

Эта проверка касается обнаруженного служебного сбоя запуска. Она не подтверждает прохождение игрового сценария или готовность новой сборки ZIP.

Продолжение: защищённый запуск распространён на оставшиеся прямые вызовы Godot в `world-gameplay.yml` — проверку формата, экспорт и получение лицензии. Каждый шаг получает отдельный заранее созданный журнал и ограничение времени; журналы сохраняются при неудаче. Сам workflow пока не запускался, поэтому это подготовленное исправление CI, а не результат облачной сборки.

Следующий выпуск этой ветки явно использует `--starter-v3` при подготовке, упаковке и проверке EXE: это предотвращает случайный возврат к прежним1001 местам вместо проверяемых1151. Чистый Windows job создаёт свои данные перед упаковкой. Дополнительно до публикации проверяются крафт, стартовые задания и экран характеристик/перенос в точном PCK. Синтаксис трёх PowerShell-блоков проверен встроенным парсером; `git diff --check` пройден. Художественная приёмка и графический тест конечного пакета остаются отдельными незавершёнными этапами.
